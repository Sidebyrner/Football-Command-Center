# Project portfolio

A single ledger across every coding project, built to answer one question well:
**given the energy and time I have right now, what should I work on next?**

## Where things live

| Thing | Path |
|---|---|
| Ledger (source of truth) | `projects/<slug>.json` — one file per project |
| CLI | `scripts/portfolio.mjs` |
| Generated board | `PORTFOLIO.md` — regenerated by `board`, never hand-edit |
| Session inbox | `~/.claude/portfolio-inbox/*.json` — dropped by the `Stop` hook |

Run everything from the portfolio repo root. If you are in a different
project's repo, the ledger is not here — say so rather than creating a
stray `projects/` directory.

## The three verbs

### 1. `pick` — what should I work on?

This is the one the user reaches for most. Translate their words into the flags:

| They say | Flags |
|---|---|
| "I'm fried" / "something easy" / "low energy" | `--energy quick` |
| "I have a normal amount of focus" | `--energy medium` |
| "I've got a real block of time" / "let's go deep" | `--energy deep` |
| "I have 45 minutes" | `--minutes 45` |
| "just the football stuff" | `--tag fantasy-football` |

```bash
node scripts/portfolio.mjs pick --energy quick --minutes 30
```

`--energy` is a **ceiling**, not an exact match: `deep` includes quick and
medium work too. Default is `deep` (everything) when they don't say.

Present the top result as a recommendation, not a list dump. Give the project,
the literal next action, and the one-line reason it surfaced. Offer the runners-up
in a sentence. Then offer to start the work.

### 2. `log` — record what just happened

Run this at the end of any session where real work happened, and whenever the
user says to note where things stand.

```bash
node scripts/portfolio.mjs log football-command-center \
  --summary "Built the Moneyball widget and wired it into /research" \
  --next "Add RB cohort percentiles to the eval engine" \
  --energy deep --minutes 120 \
  --next-why "widget renders but RB scores are still WR-weighted"
```

**Always set `--next` when you log.** A log entry without a fresh next action is
how the ledger rots — the next `pick` has nothing to offer and the project goes
quiet. If the work is genuinely finished, use `--status shipped` instead.

Write `--next` as a literal first move someone could start cold, not a theme.
"Add RB cohort percentiles to evaluationEngine.js" is usable; "improve the
eval engine" is not.

### 3. `board` — show the whole portfolio

```bash
node scripts/portfolio.mjs board          # active, paused, ideas
node scripts/portfolio.mjs board --all    # plus shipped and archived
```

Also rewrites `PORTFOLIO.md`. Commit that file alongside ledger changes.

## Supporting commands

```bash
portfolio set <slug> --status paused --why "on hold until the season ends"
portfolio set <slug> --blocked "waiting on Sleeper API key"   # drops it out of pick
portfolio set <slug> --unblock
portfolio set <slug> --backlog "Fix mobile nav overflow" --backlog-energy quick --backlog-minutes 15
portfolio new <slug> --name "Display Name" --repo owner/name --status active
portfolio inbox                # preview auto-captured sessions
portfolio inbox --drain        # fold them into the ledger
portfolio validate             # schema + consistency check
```

## Field reference

**`status`** — `active` (in flight), `paused` (deliberately set down), `idea`
(not started), `shipped` (done and in use), `archived` (dead, kept for history).

**`health`** — `on-track`, `at-risk`, `stalled`, `unknown`. Nudges ranking;
`at-risk` and `stalled` surface sooner.

**`energy`** — the axis that makes this tool worth having. Judge it by the
**context load**, not the line count:

- `quick` — no ramp-up. Copy tweaks, dependency bumps, a known one-line fix, cleaning up a TODO. The kind of thing that survives a tired evening.
- `medium` — one file or one clear seam. You need to remember how the module works, but not how the system fits together.
- `deep` — needs the whole model in your head. Architecture, cross-cutting refactors, anything touching state shape or data flow, or any work whose shape isn't decided yet.

When in doubt, rate **up**. A `quick` task that turns out to be `deep` at 10pm is
the failure mode this tool exists to prevent.

**`minutes`** — honest estimate for the next action alone, not the whole project.

**`blocked_by`** — free text. Non-null removes the project from `pick` entirely,
so only use it for genuine external blockers, not "I don't feel like it."

## Working rules

- **Never hand-edit `projects/*.json` when a command can do it.** The CLI keeps
  `last_touched`, log ordering, and triage flags consistent; hand edits drift.
- **One project's file per change.** It keeps the git history readable as a real
  changelog of the portfolio.
- **`needs_triage: true`** means the project was seeded from a repo list and nobody
  has confirmed its status or next action yet. Clear it by setting a real `--next`.
  When the user asks what to work on and many projects are untriaged, say so —
  `pick` can only be as good as the ledger.
- **Don't invent a next action.** If you don't know what a project needs, look at
  the repo, or ask. A plausible-sounding fabricated next action is worse than a
  blank, because it looks trustworthy in a board.
- Commit ledger changes with a plain message: `portfolio: log football-command-center`.

## Triage flow

When the user wants to clean up the backlog of untriaged projects, work one at a
time — read the repo's README and recent commits, propose a status, next action,
energy and estimate, confirm, then `set`. Don't batch-guess a dozen projects in
one pass; that produces a ledger nobody trusts.
